## Phase 8 — SOLID & Design Patterns

- [x] SOLID audit: split fat repository interfaces (ISP), invert concrete deps to injection tokens (DIP), document each principle with a before/after in `docs/solid.md` — `UsersRepository` split into `UserReader`/`UserWriter`/`UserPreferencesStore` behind `Symbol` tokens, ownership rules extracted to `UserAccessPolicy`, and a shared store contract run against both the Prisma adapter and a new in-memory implementation (PR #24)
- [x] Factory pattern: `PaymentProviderFactory` resolving Stripe/PayPal/mock at runtime from config — resolution is per call rather than a boot-time `useFactory` binding, and the factory is built from an injected `PAYMENT_PROVIDERS` collection so it names no implementation; both real gateways go over their REST APIs (PayPal deprecated its server SDK). Neither gateway leaves its terminal status when money is refunded, so the refunded total decides the tail of the lifecycle — read off Stripe's expanded `latest_charge` and off PayPal's `payments.refunds` minus the FAILED/CANCELLED ones. Buyer approval could not be hidden behind the port, so `authorize()` may return `requires_action` with a redirect or client secret. One behavioural contract runs against all three providers, the HTTP pair driven by in-process API fakes. Selecting a gateway without its credentials is now a boot failure. `Stripe-Version` is sent only when `STRIPE_API_VERSION` is set: a dated version string Stripe does not recognise is a 400 on every request and none could be verified from CI (PR #25)
- [x] Strategy pattern: pluggable `NotificationStrategy` (email, SMS, push) selected per user preference — `NotificationChannel` is the strategy and `NotificationDispatcher` the context, selecting in four stages (preferences, registered, configured, reachable) and reporting why each channel was dropped. Channels are attempted concurrently and each catches its own failure, so one dead transport neither aborts nor delays the others and nothing throws at the caller. Preferences fully govern marketing; a transactional message whose user disabled every channel still goes out by email, as a floor rather than an override. `sent` and `queued` are distinct because email hands off to BullMQ rather than to a third party. Twilio and Expo go over their REST APIs, driven in tests by in-process fakes. Push requires `EXPO_ACCESS_TOKEN` to count as configured — Expo's endpoint accepts unauthenticated requests, so anyone holding a device token could otherwise push to it. Fixed a pre-existing data-loss bug on the way: a patch arrives as a DTO instance whose untouched fields are `undefined`, so `{...current, ...patch}` erased every preference the caller did not name (PR #26)
- [x] Decorator pattern: `@Cacheable()`, `@Retry()`, `@Timed()` method decorators built on `Reflect.metadata` — the decorators only write metadata, because one runs while the class body is evaluated and has no cache or clock to close over; `AspectWeaver` reads it back on `onModuleInit` and installs chains over the injected collaborators. Weaving covers singleton providers and reports the two cases it cannot reach rather than silently no-op on them: `registerRouter()` runs before `callInitHook()`, so a controller's handler is already bound, and Nest keeps an `Object.create(prototype)` placeholder for request/transient providers, so the presence of an instance proves nothing. Composition order is fixed by the weaver (Timed → Cacheable → Retry), so a cache hit costs no retries and the recorded duration includes the backoff the caller waited through. Cached values are boxed so a resolved `undefined` is a hit; rejections are never cached; concurrent misses collapse into one call; an unkeyable argument, a dead store or a failed write degrade to calling through, since a cache may never turn a working call into a failing one (PR #27)
- [x] Observer pattern: typed domain event bus on `EventEmitter2` with `@OnEvent` handlers — `DomainEventPayloads` is the one catalogue of names and shapes, and `@OnDomainEvent(name)` wraps `@OnEvent` to constrain a handler's parameter to that event, so a renamed payload field is a compile error rather than a runtime `undefined` in a subscriber nobody grepped for. It also wraps the method: listeners run on the publisher's stack, so an uncontained failure would fail the operation that emitted the event — the exact coupling the pattern removes. The framework's own catch was not enough, because it logs `error.message` with no event, id or handler, and a swallowed rejection is indistinguishable from a handler that returned nothing, so nothing could report _which_ subscriber failed. `publish` returns once handlers have started and is deliberately not `async`; `publishAndSettle` waits and names every outcome. Wired to `user.registered` (both real registration paths, not the Google link-to-existing one) and `user.deleted`, which carries the address because the row is gone by the time a subscriber runs; `WelcomeEmailListener` subscribes and gave `sendWelcomeEmail` its first caller. Delivery is in-process and in-memory, so nothing survives a crash or reaches another replica — the outbox item in Phase 9 is the fix, and `docs/events.md` says not to put anything a user would notice missing on the bus (PR #28)
- [x] Adapter pattern: `StorageAdapter` interface with S3, local-disk, and in-memory implementations — the port is written to S3's semantics (flat keyspace, atomic whole-object writes) because that is the direction the mismatch survives; `STORAGE_ADAPTER` selects one at boot and nothing else in `src` names an implementation. Presigning is a separate interface rather than a method that throws on two of three backends, since a signature is something the _store_ verifies and a disk has nothing to verify one with — the endpoints answer 501, not 503, because no configuration will ever make them work. One behavioural contract runs against all three and immediately caught the in-memory adapter throwing _synchronously_ where the others rejected, which would have crashed any caller using `.catch()` against the one backend every other suite runs on. It also forced two divergences closed rather than documented: keys are validated against the stricter of S3's and the filesystem's limits (including a 255-byte-per-segment cap S3 does not impose), and the local adapter stores each key as a directory holding `.object`/`.meta.json`, because `<root>/<key>` cannot hold `a/b` and `a/b/c` at once — `avatars/<id>` beside `avatars/<id>/thumb` would have worked on S3 and failed on disk. Two real defects fixed on the way: the presigner signed `host` alone, making `ContentType` a suggestion a client could ignore to serve `text/html` from the bucket's own origin, and `STORAGE_ADAPTER=memory` is now refused at boot in production, since unlike every other misconfiguration it raises no error anyone sees — uploads succeed and the files are gone after a restart. S3 is driven in tests by an in-process fake of its HTTP API installed as the SDK's `requestHandler`, reached through the same optional DI token an operator would use to tune retries, so no test-only branch exists in the adapter (PR #29)
- [x] Provider scopes: DEFAULT vs REQUEST vs TRANSIENT demo module + `docs/di-scopes.md` on the request-scoped performance trap — the demo is built around the failure rather than the taxonomy: `AuditTrailService` is a plain `@Injectable()` whose accumulate-then-flush buffer never sees more than one request, because it injects a request-scoped provider four lines away, and `DiScopesController` inherits the scope in turn without declaring anything. `SingletonAuditTrail` is the same class with the correlation id passed as an argument, and `RequestContextResolver` is the escape hatch for where that cannot reach — `ModuleRef.resolve` keyed by the request's own context id, which returns the instance the router already built rather than a second one. `ScopeAudit` reads back `InstanceWrapper.isDependencyTreeStatic()` — the computation Nest itself uses — and names both the components rebuilt per request and the dependency chain responsible; the e2e suite pins the exact set, so injecting a request-scoped provider into `UsersService` turns CI red instead of silently converting half the container. Measured rather than asserted (`pnpm bench:scopes`): resolution goes 0.5µs → ~36µs, but end to end that is 11–22% on a handler that does nothing and unmeasurable next to one Postgres round trip, so the doc's thesis is the memoised state a singleton stops keeping, not the microseconds. Two framework behaviours it relies on are pinned by `scope-caveats.spec.ts`: lifecycle hooks never fire on a request-scoped provider, and a request-scoped global enhancer is rebuilt for every route in the application. Two defects fixed on the way — the resolver minted a fresh context per call for any carrier the router never touched, and the ledger kept every instance id forever, a leak on a per-request provider (PR #30)

## Phase 9 — Concurrency & Data Integrity

- [x] Idempotency middleware: `Idempotency-Key` header, Redis dedupe store, replay of the original response on retry — a global interceptor plus a two-implementation store port. The response is captured at `res.send` rather than from the handler's return value, because what has to be replayed is the bytes the client received, and those only exist after the envelope interceptor has wrapped them or `AllExceptionsFilter` has rendered them — which is also why a filter-rendered 4xx replays like any other outcome and why the interceptor is bound above the envelope. Only `reserve` has to be atomic, which is what makes the store a port rather than a `Map`: Redis settles the race with `SET NX`, the in-memory store settles it with the event loop, so it is honest for one process only and is refused in production. Reservations carry a fencing lease (checked and written in one Lua script) so a request that outlived its own reservation cannot release the retry that replaced it. An unreachable store fails closed with 503, since running the handler when the server cannot tell a first attempt from a retry is exactly how a client gets charged twice. Statuses follow draft-ietf-httpapi-idempotency-key-header: 409 in flight, 422 for a key reused on a different request. Two defects fixed on the way — `LoggingInterceptor` used `tap`, so a request answered by an interceptor that completes without emitting produced no access-log line at all, and an unreadable value squatting on a Redis key would have made `reserve` throw on every retry until the TTL cleared it. Multipart uploads are fingerprinted by `Content-Length` rather than content, documented rather than papered over (PR #31)
- [x] Optimistic concurrency: `version` column + `ETag`/`If-Match` on mutating endpoints, 412 on conflict — the validator is the version counter rather than a digest of the response body, because `meta.timestamp` in the envelope makes Express's default weak `ETag` change on every request and fail `If-Match` against a resource nobody touched. The predicate rides in the `WHERE` of the write itself, so there is no window between checking and writing; Prisma reports "no row matched" as P2025 whether the row is absent or at another version — a 404 and a 412 — so the adapter tells them apart by reading the row back rather than parsing the error, which is also what keeps the classification correct against the in-memory store the e2e suite runs the whole application on. Requiring the header could not live in a guard, an interceptor, or a throwing parameter decorator: all three run before the handler's own checks, and RFC 9110 §13.2.1 puts preconditions _after_ them — the first cut enforced it in the param decorator and 17 e2e tests went red with 428 where they expected 400 or 403. The order is now 401/403 → 400 → 404 → 428 → 412 → write, pinned end to end. Preferences share the user's version, since they are a JSON column on that row; conservative on purpose, because one row with two validators is how a client sends the wrong one. Two pre-existing bugs fixed on the way: `GET /users/:id` was cached under the request URL while `invalidateUserCache` deleted `v1:users:<id>`, so every write left the read stale for the full 30s TTL — quiet before, a non-terminating retry loop once the stale read hands out a stale validator — and `setPreferences` was a racy read-modify-write whose second writer silently discarded the first one's field. Not done: `If-None-Match`/304 on reads, and no resource but `User` carries a version yet (PR #32)
- [x] Pessimistic locking: `SELECT ... FOR UPDATE` inside a Prisma interactive transaction — `lockRows` takes the lock, and the pattern it enforces is lock → re-read → write in one transaction, because everything read before the lock may already be stale. It sorts its keys, since `LockRows` sits above `Sort` in the plan: two callers locking overlapping sets then agree on the order and cannot deadlock against each other, which locking in whatever order a scan returned is how you earn a `40P01` you cannot reproduce. Lock strength is a parameter rather than a constant for a reason checked against a real server rather than asserted: inserting a child row takes `FOR KEY SHARE` on its parent, which conflicts with `FOR UPDATE` and not with `FOR NO KEY UPDATE`, so locking a `users` row the strong way to serialise an edit would also stall every concurrent login and refresh for that account. `NOWAIT` and `lock_timeout` both report SQLSTATE `55P03` and differ only in message text, so both become one `LockUnavailableError` — the recourse is identical. The call site is refresh-token rotation, where `refresh` used to read the row, check it, then delete it by id: both concurrent requests found the row and only the `DELETE` separated them, raising P2025 on a row the winner had already removed, so the loser was answered **500** where the truthful answer is 401. The token was single-use throughout — this is not a replay hole — but the property lived in whichever statement happened to be last, and `deleteMany` (which `logout` already uses, and which reports a count instead of raising) would have turned one token into two live families with nothing to notice. It is now `RefreshTokenStore.consume`'s stated contract, run against Postgres and against an in-memory double that serialises claims through a per-token promise chain so it satisfies the exclusion honestly rather than by looking like it. Two pre-existing defects fixed on the way: the repository had **no initial migration** — every migration was an `ALTER TABLE` against tables nothing ever created, so `prisma migrate deploy` failed on its first statement against a clean database and no job had ever run it — and `pnpm format:check` was failing on `main` over a stray emphasis marker. New `pnpm test:db` gate, deliberately with no skip-if-absent branch, since a lock suite that passes without a database reports that the database behaves correctly while never having asked it (PR #33)
- [x] Distributed lock via Redlock exposed as a `@Lock()` decorator with TTL + fencing token — a `DistributedLock` port with two implementations, and the decorator installed by the existing `AspectWeaver` rather than a second weaving mechanism, at `@Timed → @Cacheable → @Lock → @Retry → method`: a cache hit takes no lock, and retries run _inside_ it, since a ladder run outside would drop the exclusion between attempts. Redlock rather than one primary with replicas because replication is asynchronous — a lock acknowledged and not yet replicated is simply absent from the replica that gets promoted. The lease is not treated as the guarantee: Kleppmann's critique is right that a stopped process cannot notice it has been stopped, so every acquisition carries a strictly increasing `fencingToken` and the resource is expected to refuse anything lower. Making that token monotonic _across a quorum_ is the part usually left out and takes two phases — `SET NX` and `INCR` in one Lua script, so a node cannot issue a token for a lock it did not grant, then the issued token published back to a majority, because a node that refused an acquisition never incremented and a later quorum of laggards would otherwise reissue a token already in use. One counter per node shared by every key, with no TTL: an expiring counter restarts at 1, which a resource that has accepted token 5,000 refuses forever. Nothing degrades quietly, unlike the other aspects — an unkeyable argument throws where `@Cacheable()` calls through, `@Lock()` on a controller or a request-scoped provider is a boot failure rather than a warning, and a lease that lapsed mid-flight throws `LockLostError` even when the method returned a value. Elapsed time is read from `performance.now()`, never `Date.now()`, which NTP can step backwards and so inflate a validity. One behavioural contract runs against four topologies — in-memory, one real node, three, and three with one down — since a quorum is not something a mock can have. Two defects fixed on the way: `onModuleDestroy` now `disconnect()`s after `QUIT`, because a node that is down never answers it and ioredis's retry timer kept the process alive, and the module waits (bounded) for the clients to be ready, since `enableOfflineQueue: false` fails a command issued before the socket is up — the first acquisition after every deploy. CI gained two more Redis services; `docker-compose.yml` could not boot its `api` service at all beforehand, because `NODE_ENV=production` there already refused the in-memory storage and idempotency defaults. Not done: no production call site takes a lock yet (as with `@Cacheable()`/`@Retry()`/`@Timed()`), no fairness, no re-entrancy, and no `fencingToken` column on any model (PR #34)
- [x] CPU-bound work offloaded to a `worker_threads` pool (piscina) with a bounded queue — `WorkerPool` port with a Piscina adapter and an in-process `inline` stand-in, pinned by one contract spec against both (the real leg spins up `worker_threads` via ts-node, covering the `postMessage` boundary a mock cannot). `WORKER_POOL_MAX_QUEUE` (total outstanding = queued + running) rejects overflow synchronously with `WorkerPoolSaturatedError` — Piscina's own `Infinity` default is the memory leak the bound exists to prevent — and Piscina's internal `maxQueue` is set to `port.maxQueue - maxThreads` so both adapters saturate on the same submission count. Aborts and timeouts tear down the caller's wait, not the worker (Piscina cannot cancel a running task); `docs/worker-pool.md` says so. Tasks `csv.encode`/`sha256.hex`/`test.sleep` augment `WorkerTaskMap` so a task without a handler is a compile error. No production call site injects the pool yet (PR #35)
- [x] Immutability: `readonly` DTOs, deep-freeze in dev, structural-sharing update helpers — the three are one change, because adopting them in the usual order is unsafe: structural sharing looks like an allocation optimisation, but once an update returns its input unchanged, `prefs.timezone = …` on "my own copy" writes to the value the store is still holding, and for a user who has never set a preference that value is `DEFAULT_USER_PREFERENCES` itself. Freezing is what makes sharing safe to adopt at all; the `readonly` types are what carry the rule into production, where the freeze is off. `deepFreeze` handles four things a five-line recursive freeze does not, each checked against Node first rather than assumed: `Object.freeze` _throws_ on a non-empty `Buffer` or typed array, so the naive version crashes on binary payloads rather than degrading; a visited set makes `a.self = a` terminate; traversal reads property _descriptors_ so no getter is invoked during what should be an inert walk; and non-enumerable and symbol-keyed properties are covered. What it cannot do is documented rather than papered over — frozen `Map`, `Set` and `Date` mutators still work, since that state is in internal slots, which is why `DeepReadonly` maps them to `ReadonlyMap`/`ReadonlySet` and the type layer is the only layer doing that work. The guard is loud at all only because `strict: true` implies `alwaysStrict`, so a test pins that dependency on the tsconfig. `DeepFreezePipe` is bound after `ValidationPipe` (global pipes run in registration order) and touches only user-defined metatypes: `type: "custom"` (`@Req()`, `@Res()`, `@UploadedFile()`, `@CurrentUser()`) and native metatypes are values Express owns and keeps mutating, and freezing a request would break the framework outright. The helpers preserve frozen-ness deliberately, since otherwise the guard would be conditional on the data — a no-op update returning the frozen input and throwing, a real one returning a thawed copy and not. `mergePreferences` is now `patch` and `DEFAULT_USER_PREFERENCES` is frozen _unconditionally_, giving two properties the store contract now asserts for every implementation: preferences handed out are deeply frozen even in production, and every user with nothing stored gets the same defaults object. The e2e suite runs with freezing on and found no handler that mutates its own payload, so nothing had to change to accommodate it; a new e2e case asserts a frozen DTO arrives through the real pipe chain, so unwiring the pipe fails a test instead of silently going inert. Not done: nothing consumes the no-op signal yet, and both in-memory fakes still hand out their own `User` map entries — a pre-existing divergence from Prisma left alone (PR #36)
